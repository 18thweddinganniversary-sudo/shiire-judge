# せどりGO 統合設計

Date: 2026-09-16
Status: design approved in conversation; written spec pending user review

## 1. 目的

現在の「仕入れ判断アプリ」を捨てずに、せどりの買付け全体を支援する「せどりGO」へ発展させる。

せどりGOの目的は、ユーザーの代わりに仕入れを決めることではない。ネット上で候補を絞り、店頭で必要な判断材料をすぐ出し、結果を次回に活かすことで、買付けの手間と無駄な探索を減らすこと。

最終判断は常にユーザーが行う。

## 2. 共通設計思想

- サポート優先。アプリは判断材料を整理して提示する。
- 最終判断はユーザーに委ねる。
- 人をアプリに合わせず、実際の買付け行動にアプリを合わせる。
- 店頭で大量に闇雲スキャンする前提にしない。
- 事前に候補を絞り、店舗では「見つける・価格を見る・最終確認する」に集中させる。
- 実データと実店舗での結果を次回の候補探索へ活かす。
- 🟢は「条件上、仕入れ候補として良好」の意味であり、「買え」という命令ではない。
- アカウント固有の出品可否は自動推測せず、候補商品だけSeller Central/FBAでユーザーが確認する。

## 3. 製品構成

せどりGOは1つのアプリとして、以下の3機能を持つ。

### A. 候補を探す

店へ行く前に、実データを使って仕入れ候補を絞る。

候補一覧で最低限表示する情報:
- JAN
- 商品名
- 現在Amazon価格
- 90日平均価格
- 出品者数
- Amazon本体の有無
- 回転/需要指標
- 仕入れ上限価格
- 候補理由
- 最終確認が必要な項目

「狙い目店舗」は、根拠がある場合のみ補助情報として表示する。根拠のない店舗名を推測しない。

### B. 店頭で判定

現在の仕入れ判断アプリの強みをそのまま中核機能として残す。

- JANスキャンまたは候補一覧から商品を開く
- 店頭価格を入力する
- `decision-engine.js` の同一基準で判定する
- 🟢/🔴と、その理由を表示する
- 利益、利益率、ROI、仕入れ上限を表示する
- ユーザーが最終判断する

既存の合格済み仕様は回帰させない。

### C. 結果を記録

候補が実際にどうなったかを残す。

最小記録項目:
- JAN
- 店舗
- 店頭価格
- 判定結果
- ユーザー判断（仕入れた / 見送った）
- 日時

将来は、この実績を候補探索の優先順位改善に使う。

## 4. データフロー

1. 候補探索が商品候補を収集する。
2. 候補ごとに必要データを取得する。
3. 現在の判定基準を再利用し、「条件を満たし得る候補」だけを残す。
4. 仕入れ上限を算出する。
5. ユーザーが候補一覧を見る。
6. 店舗で商品を見つける。
7. 店頭価格を入力する。
8. 同じ判定エンジンで最終判定する。
9. ユーザーが仕入れるか決める。
10. 結果を保存し、次回の支援材料にする。

## 5. 候補探索方式

候補探索は新しいサブシステムなので、最初から特定APIに固定しない。

実装前の最初の技術検証で、次を比較する。

### 方式1: Keepaの検索/候補抽出機能を利用

長所:
- Amazon市場データとの距離が近い
- 現在の判定データと接続しやすい

注意:
- 利用可能な検索API・プラン条件・トークン費用を実測/公式仕様で確認する必要がある
- 既存の1 token/商品運用を壊さないこと

### 方式2: 外部の商品カタログ/店舗・EC情報から候補JANを集め、Keepaで精査

長所:
- 店舗で見つかる商品の母集団に寄せやすい可能性がある

注意:
- JAN精度、利用規約、取得安定性を確認する必要がある
- 情報源ごとに品質差が大きい

### 方式3: ユーザーが得意カテゴリ/店舗の種を指定し、そこから候補探索

長所:
- 無駄な全商品探索を避けやすい
- Ver.1として小さく始められる

注意:
- 完全自動ではない

### Ver.1方針

方式1を最初に技術検証し、成立しなければ方式2/3へ切り替える。

ただし、Keepaトークンを大量消費する総当たり探索は禁止する。候補抽出段階で絞り込み、詳細取得は候補だけに限定する。

## 6. 判定基準

Ver.1では現在の正本を変更しない。

- データ鮮度: 6時間以内
- 最低利益: 500円
- 最低粗利率: 20%
- 最低ROI: 20%
- 出品者数: 15以下
- 需要レベル: 2以上
- 現在価格 / 90日平均価格: 0.75〜1.15
- 判定ロジック正本: `decision-engine.js`

候補探索と店頭判定で別々の基準を持たない。

候補探索時点では店頭仕入れ価格が不明なため、「仕入れ上限価格」を算出し、その価格以下なら他条件上は🟢候補になり得る、と表示する。

## 7. UI方針

スマホ縦を最優先する。

ホームの主要導線は2本に絞る。

- 「候補を探す」
- 「店頭で判定」

候補一覧は大量のKeepa情報を見せず、買付けに必要な情報だけを優先する。

候補カードの主表示:
- 商品名
- 仕入れ上限
- Amazon価格
- 出品者数
- Amazon本体の有無
- 回転の要約

詳細を開けば理由と数値を確認できる。

## 8. エラー・不確実性

- データ不足は🟢にしない。
- API失敗を商品不存在として扱わない。
- 古いデータは明示する。
- 候補探索で取得できない項目は「未確認」と表示する。
- 店舗在庫は、確認できる信頼できるデータ源がない限り「在庫あり」と断定しない。
- 出品規制は公開情報から推測せず、ユーザー確認項目として残す。

## 9. Ver.1でやらないこと

- 自動購入
- ユーザーの代わりの最終仕入れ決定
- SP-API Gate0
- 根拠のない店舗在庫予測
- 全Amazon商品を総当たりする大量Keepa取得
- 判定基準を緩めて候補数を増やすこと
- 既存の店頭判定機能の大規模作り直し

## 10. 実装順

### Phase 1: 候補探索の技術検証

目的: 少ないAPI消費で、🟢になり得る候補JANを再現可能に抽出できるか確認する。

合格条件:
- 候補抽出経路が説明可能
- API/トークン費用が測定できる
- 候補が現在のdecision-engine基準と整合する
- 総当たりにならない

### Phase 2: 候補一覧

Phase 1の候補をアプリ内で一覧表示する。

### Phase 3: 店頭判定との接続

候補一覧から既存の店頭判定へ1タップで移行する。

### Phase 4: 買付け結果の記録

仕入れた/見送った結果を保存する。

### Phase 5: 実店舗フィードバック

実際の候補発見率・価格差・見送り理由を集計し、候補探索の優先順位改善に使う。

## 11. 成功条件

せどりGO Ver.1は、単に候補をたくさん出すことを成功としない。

成功とは:
- 店へ行く前に見る商品を減らせる
- 店頭での無駄なスキャンを減らせる
- 候補ごとに仕入れ上限が分かる
- 店頭で既存の信頼できる判定が使える
- 最終判断はユーザーが行える
- 実際の買付け結果が次回の支援につながる

## 12. 既存アプリとの関係

「仕入れ判断アプリ」は廃止しない。現在の機能・判定エンジン・実績を、せどりGOの「店頭で判定」機能として吸収する。

既存合格項目を壊してまで名称変更や画面再構成を優先しない。統合は段階的に行う。

## 13. チャッピーループ問題への対策

せどりGOの開発では、AIとの長期共同作業で同じ調査・同じ修正・同じ確認を繰り返すこと自体を品質問題として扱う。

### 開始時
- 毎回 `MASTER_SPEC.md`、`PROJECT_STATUS.md`、`TEST_MATRIX.md`、現在コードを先に確認する。
- 合格済み項目と未完項目を分離し、合格済みを最初からやり直さない。
- 過去チャットの記憶よりGitHub上の正本を優先する。

### 修正時
- 新しい修正を出す前に「前回の指示 → Work/実装の差分 → 本番/実機結果」を照合する。
- 原因を `指示設計 / 実装 / 外部API・データ・環境` のどこにあるか切り分ける。
- 原因不明のまま同じ場所へ修正を重ねない。
- 同じ症状が繰り返した場合は、場当たり修正を止めて根本原因を再監査する。

### ユーザー負担
- ユーザーは主に実機でしか取れない事実を伝える。
- コード、Git差分、ログ、API、自動テストでAI側が確認できることを、スクリーンショットや手作業でユーザーへ戻さない。
- 同じスクリーンショット・同じ確認を繰り返し要求しない。
- ユーザー操作が本当に必要になる地点まで、AI側で進められる作業を先に進める。

### 完了管理
- 1項目を `調査 → 原因特定 → 修正 → テスト → 本番反映 → 本番確認 → 記録` まで閉じる。
- WorkやAIの「できた」という文章だけで合格させない。
- 合格証拠を `PROJECT_STATUS.md` / `TEST_MATRIX.md` に残す。
- 次回は最後に残した未完1項目から再開する。
- Keepaトークン、Workクレジット、実機確認時間など有限資源を、確認済み事項の再検証で浪費しない。

この対策はせどりGO固有ではなく、チャッピーGO、現場管理アプリ、その他の今後の開発物にも共通適用する。
